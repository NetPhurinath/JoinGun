## 1. วัตถุประสงค์

แผนนี้อธิบายว่าทีมจะแสดงอย่างไรว่า MVP ของ JoinGun ทำงานตามที่ spec กำหนด ทำตามข้อกำหนดใน `rule.md` และช่วยให้นักศึกษาหาเพื่อนร่วมทำกิจกรรมได้จริง โดยตอบสองคำถาม:

1. **ทำงานตามข้อกำหนดหรือไม่** (verification) — test อัตโนมัติ, การตรวจ end-to-end บนเบราว์เซอร์, การวัดด้าน non-functional และการตรวจด้าน compliance โดยแต่ละรายการโยงกับรหัส F/NFR/LR, รายการ backlog หรือข้อใน `rule.md`
2. **มีประโยชน์และใช้งานได้จริงสำหรับนักศึกษาหรือไม่** (validation) — ทดสอบกับนักศึกษาจริงแบบมีผู้ดำเนินการอย่างน้อย 10 sessions เปรียบเทียบผลการทำงาน **ก่อน** (วิธีที่ใช้อยู่ตอนนี้ คือกลุ่มแชตและโซเชียลมีเดีย) กับ **หลัง** (JoinGun) พร้อมแบบสอบถาม SUS และ TAM

## 2. ขอบเขต

### 2.1 Core workflow (MUST)

MUST workflow ที่ล็อกไว้คือ **"เข้าร่วมกิจกรรมจากฟีด"** ([feature list](../02-design/feature-list.md), [user journey](../02-design/user-journey.md)): นักศึกษาที่เข้าสู่ระบบแล้วดูและกรองฟีด เปิดกิจกรรม ดูจุดนัด เข้าร่วมพร้อมให้ความยินยอมเก็บประวัติการเข้าร่วม และได้รับการเตือน requirement ที่เกี่ยวข้องคือ F1 (เข้าสู่ระบบ), F2 (กิจกรรมพร้อมหมุดแผนที่), F3 (ฟีดและตัวกรอง) และ backlog 2.4 (เข้าร่วม) session กับผู้ใช้ (§5) ทดสอบเฉพาะ workflow นี้ ส่วนอื่นด้านล่างทีมทดสอบเองในระดับระบบ

## 3. ระดับการทดสอบ

ระดับการทดสอบเป็นไปตาม Testing Pyramid ของรายวิชา (Unit → Integration → E2E แล้วจึง UAT กับผู้ใช้จริง):

- **Unit / ระดับโมดูล:** test ที่เรียกโมดูลของเซิร์ฟเวอร์โดยตรง — `profile-crypto.test.js` (การเข้ารหัสฟิลด์) และฟังก์ชันด้าน security และ auth ที่ `auth.test.js` เรียกโดยตรง ยังไม่มี unit test แบบแยกขาดจริง ๆ ชั้นนี้จึงบางที่สุด
- **Integration:** test ส่วนใหญ่ใน 47 tests ของ `server/test/` เปิดแอป Express จริงบนฐานข้อมูล SQLite ชั่วคราวแล้วเรียก HTTP API จึงตรวจการตรวจข้อมูล การควบคุมสิทธิ์ บันทึก และ transaction ไปพร้อมกัน
- **E2E:** UI จริงทำงานกับเซิร์ฟเวอร์จริง (Playwright เมื่อได้รับอนุมัติ ระหว่างนี้ทำขั้นตอนเดียวกันด้วยมือ)
- **UAT:** นักศึกษาจริงทำ core workflow (§5)

## 5. การทดสอบการยอมรับโดยผู้ใช้ (UAT) กับผู้ใช้จริง

### 5.1 รูปแบบ

- **อย่างน้อย 10 sessions ที่ทำครบ วางแผนไว้ 12** (U01–U12) และคนสำรอง 2 คน (U13–U14) เพื่อให้มีคนไม่มาแล้วจำนวนไม่ต่ำกว่า 10 session นำร่อง (U00) กับคนที่ไม่อยู่ในกลุ่มตัวอย่างไม่นับรวม
- **มีผู้ดำเนินการ ผู้เข้าร่วมทีละคน ประมาณ 30–35 นาที** แบบพบตัวในมหาวิทยาลัย Moderator เป็นคนให้งาน Note-taker จับเวลาและจดบันทึก ให้ผู้เข้าร่วมพูดสิ่งที่คิดออกมา (think-aloud) ผู้ดำเนินการบอกว่า "เรากำลังทดสอบระบบ ไม่ได้ทดสอบคุณ" และไม่ช่วยหรือชี้ งานที่ติดจนเกินเวลาจำกัดนับว่าไม่สำเร็จ
- **สองรอบ** ตามที่สไลด์แนะนำ (ทดสอบ 5 → แก้ → ทดสอบอีก 5): รอบ 1 (U01–U06) **วันพุธที่ 4 พ.ย.** แก้ปัญหาร้ายแรง แล้วรอบ 2 (U07–U12) วันที่ 7–8 พ.ย. ปัญหาที่พบในรอบ 1 ไม่ควรเกิดซ้ำในรอบ 2
- **ก่อน vs หลัง** เป็นการเปรียบเทียบภายในคนเดียวกัน: ผู้เข้าร่วมแต่ละคนทำงานหลักด้วย **วิธีที่ใช้อยู่ตอนนี้** (กลุ่มแชต, "ก่อน") ก่อน แล้วจึงทำ **ด้วย JoinGun** ("หลัง") ตามที่สไลด์กำหนด (ทำวิธีเดิมก่อนเพื่อได้เวลาฐาน) สองเงื่อนไขใช้สถานการณ์ต่างกันแต่เทียบเท่ากัน (ชุด A: แบดมินตัน สำหรับ "ก่อน", ชุด B: ฟุตซอล สำหรับ "หลัง") เพื่อไม่ให้ผู้เข้าร่วมจำคำตอบได้ ลำดับที่ตายตัวเป็นข้อจำกัด (§11)

### 5.3 จริยธรรมและข้อมูลส่วนบุคคลของผู้เข้าร่วม

- ขอความยินยอมอย่างมีข้อมูล (PDPA) ก่อนทุก session: เอกสารข้อมูลสำหรับผู้เข้าร่วมและแบบยินยอมภาษาไทย บอกวัตถุประสงค์ สิ่งที่บันทึก ระยะเวลาเก็บ และสิทธิ์หยุดได้ทุกเมื่อ ขอแยกอีกครั้งก่อนบันทึกเสียง วิดีโอ หรือภาพถ่าย
- ระบุผู้เข้าร่วมด้วยรหัสเท่านั้น (U01…) ชื่อและช่องทางติดต่ออยู่ในแผ่นลงทะเบียนแยกที่เปิดได้เฉพาะ QA และลบเมื่อจบรายวิชา
- บันทึก **หน้าจอและเสียงเท่านั้น** ไม่บันทึกใบหน้า เว้นแต่ผู้เข้าร่วมยินยอมให้ถ่ายภาพสำหรับนำเสนอ final แบบสอบถามไม่ถามชื่อหรืออีเมล
- ไม่นำไฟล์บันทึกดิบหรือบันทึกที่ระบุตัวตนได้เข้า Git ใส่เฉพาะผลสรุปรวมใน `test-report.md`
- จนกว่า JoinGun จะทำงานบน HTTPS (ขั้นที่ 7 ของแผนส่งมอบ) ผู้เข้าร่วม **ไม่กรอกอีเมลหรือข้อมูลส่วนตัวของตัวเอง** ให้ใช้บัญชีทดสอบที่ทีมเตรียมไว้บนโทรศัพท์ของทีม และงานสมัครสมาชิก (ถ้ามี) ใช้อีเมล `.ac.th` ทดสอบที่ทีมควบคุม (ผู้ดำเนินการอ่านรหัสให้) เมื่อ Tech Lead อนุมัติ hosting แบบ HTTPS แล้ว ผู้เข้าร่วมจึงใช้อีเมลของตัวเองบนโทรศัพท์ของตัวเองได้ ฐานข้อมูล UAT แยกจากฐานข้อมูล pilot และล้างทิ้งหลังวิเคราะห์เสร็จ

## 6. ตัวชี้วัด

### 6.1 ผลการทำงาน ก่อนและหลัง (บังคับ)

วัดต่อผู้เข้าร่วมและต่องาน:

| ตัวชี้วัด | วิธีวัด | รายงานเป็น |
| --- | --- | --- |
| ความสำเร็จของงาน | สำเร็จ / ไม่สำเร็จ (ต้องช่วยหรือเกินเวลา = ไม่สำเร็จ) | อัตราสำเร็จต่องานต่อเงื่อนไข พร้อมช่วงความเชื่อมั่น 95% แบบ adjusted-Wald |
| เวลาที่ใช้ | ตั้งแต่อ่านสถานการณ์จบจนถึงเกณฑ์สำเร็จ (เฉพาะงานที่สำเร็จ) | ค่าเฉลี่ยและมัธยฐานต่อเงื่อนไข เวลาก่อนเทียบหลัง และ % การเปลี่ยนแปลง |
| ข้อผิดพลาด | ไปผิดทาง เลือกกิจกรรมผิด ตอบจำนวนหรือเวลาผิด | ค่าเฉลี่ยต่องานต่อเงื่อนไข |
| Single Ease Question (SEQ) | "โดยรวมแล้วงานนี้…" 1 (ยากมาก) – 7 (ง่ายมาก) | มัธยฐานต่องานต่อเงื่อนไข |

การวิเคราะห์ก่อนเทียบหลัง (T1–T4): คิดผลต่างแบบจับคู่ต่อผู้เข้าร่วม ใช้ Wilcoxon signed-rank กับเวลาและ SEQ (n ≥ 10) เปรียบเทียบความสำเร็จแบบพรรณนา (และใช้ McNemar ถ้า n เพียงพอ) ด้วยผู้เข้าร่วมประมาณ 12 คน ผลเป็นสัญญาณ ไม่ใช่ข้อพิสูจน์ รายงานต้องระบุข้อนี้

รอบ 1 เทียบรอบ 2: สำหรับปัญหาจากรอบ 1 ที่แก้แล้ว เปรียบเทียบการเกิดซ้ำและความสำเร็จของงานที่เกี่ยวข้องในรอบ 2 (เชิงพรรณนาเท่านั้น เพราะเป็นคนละคน)

### 6.2 SUS (System Usability Scale; ไม่บังคับในรายวิชา แต่ใช้)

SUS มาตรฐาน 10 ข้อ (Brooke, 1996) สเกล 5 ระดับ จากไม่เห็นด้วยอย่างยิ่ง (1) ถึงเห็นด้วยอย่างยิ่ง (5) ใช้ฉบับแปลภาษาไทยที่ทีมจัดทำ (แปล แล้วให้สมาชิกอีกคนแปลกลับ แล้วตรวจใน session นำร่อง) ให้ทำทันทีหลังทำงานเสร็จ เฉพาะเกี่ยวกับ JoinGun

ข้อคำถามภาษาไทยอยู่ใน [uat-materials-th.md](uat-materials-th.md) ส่วน D ต้นฉบับภาษาอังกฤษอยู่ใน [test-plan.md](test-plan.md) §6.2

การคิดคะแนน: ข้อคี่ (คะแนน − 1) ข้อคู่ (5 − คะแนน) รวมแล้ว × 2.5 = 0–100 ต่อคน รายงานค่าเฉลี่ยและส่วนเบี่ยงเบนมาตรฐานของผู้ใช้ทั้งหมด และเกรดเทียบค่าเฉลี่ย 68 (Sauro & Lewis: ≥ 80.8 = A, < 51.7 = F) SUS ไม่ใช่เปอร์เซ็นต์

### 6.3 TAM (Technology Acceptance Model; ไม่บังคับในรายวิชา แต่ใช้)

**เลือก TAM ไม่ใช่ UTAUT2** เพราะ Habit และ Price Value ของ UTAUT2 วัดอย่างมีความหมายไม่ได้ใน session เดียวของแอปฟรี และข้อคำถามราว 28 ข้อจะทำให้ผู้ตอบล้า สาม construct หลักของ TAM ตอบคำถามของการทดสอบนี้ได้ตรง: JoinGun มีประโยชน์ ใช้ง่าย และนักศึกษาจะใช้หรือไม่ อาจพิจารณา UTAUT2 อีกครั้งสำหรับ pilot ภาคสนามหลายสัปดาห์ (ขั้นที่ 8) การเลือกนี้ให้ QA และ Product Owner ยืนยัน

ข้อคำถามดัดแปลงจาก Davis (1989) สำหรับ JoinGun สเกล 5 ระดับ (1 ไม่เห็นด้วยอย่างยิ่ง – 5 เห็นด้วยอย่างยิ่ง) แปลเป็นไทยแบบเดียวกับ SUS ให้ทำหลัง SUS

| Construct | ข้อคำถาม |
| --- | --- |
| การรับรู้ประโยชน์ (PU) | PU1 การใช้ JoinGun จะช่วยให้ฉันหาคนมาทำกิจกรรมด้วยได้เร็วขึ้น |
| | PU2 การใช้ JoinGun จะทำให้การนัดเวลาและสถานที่นัดพบง่ายขึ้น |
| | PU3 การใช้ JoinGun จะเพิ่มโอกาสให้ฉันได้เข้าร่วมกิจกรรมที่ฉันสนใจ |
| | PU4 โดยรวมแล้ว ฉันคิดว่า JoinGun มีประโยชน์ในการหาเพื่อนร่วมทำกิจกรรม |
| การรับรู้ความง่าย (PEOU) | PEOU1 การเรียนรู้วิธีใช้ JoinGun เป็นเรื่องง่ายสำหรับฉัน |
| | PEOU2 ฉันใช้ JoinGun ทำสิ่งที่ต้องการได้อย่างง่ายดาย |
| | PEOU3 การใช้งาน JoinGun ชัดเจนและเข้าใจได้ |
| | PEOU4 โดยรวมแล้ว ฉันคิดว่า JoinGun ใช้งานง่าย |
| ความตั้งใจที่จะใช้ (BI) | BI1 หาก JoinGun เปิดให้ใช้ในมหาวิทยาลัยของฉัน ฉันจะใช้ |
| | BI2 ฉันจะใช้ JoinGun หาเพื่อนร่วมทำกิจกรรมภายในเดือนหน้า |
| | BI3 ฉันจะแนะนำ JoinGun ให้เพื่อน |
| ส่วนขยาย (ไม่บังคับ): การรับรู้ความปลอดภัย (ไม่ใช่ส่วนของ TAM มาตรฐาน รายงานแยก) | SAFE1 ฉันจะรู้สึกสบายใจที่จะไปพบคนที่ฉันรู้จักผ่าน JoinGun |
| | SAFE2 JoinGun บอกชัดเจนว่าการยืนยันอีเมลสถานศึกษารับประกันอะไรได้ และอะไรไม่ได้ |

รายงานค่าเฉลี่ย ± ส่วนเบี่ยงเบนมาตรฐานต่อ construct ค่า Cronbach's alpha ต่อ construct เป็นข้อมูลประกอบเท่านั้น (ไม่เสถียรเมื่อ n ≈ 12) ไม่สรุปความเป็นเหตุเป็นผลระหว่าง PU, PEOU และ BI เพราะกลุ่มตัวอย่างเล็กเกินไปสำหรับ structural model

## 8. เกณฑ์เริ่ม หยุดชั่วคราว และจบ

**เกณฑ์เริ่ม UAT รอบ 1 (4 พ.ย.)**

**เกณฑ์จบ**

- วิเคราะห์ session ที่ทำครบแล้วอย่างน้อย 10 sessions (นับเป็น session ครบเมื่อทำ T1–T4 ครบทั้งสองเงื่อนไข และตอบ SUS/TAM ครบ)
- ไม่มีปัญหาระดับ 4 ค้างอยู่ ปัญหาระดับ 3 แก้แล้วหรือ Product Owner ยอมรับเป็นลายลักษณ์อักษร
- เขียน `test-report.md` แล้ว (§10) ทีมตรวจแล้ว และ Product Owner อนุมัติ UAT
